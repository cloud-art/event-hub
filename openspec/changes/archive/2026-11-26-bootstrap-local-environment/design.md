# Design

## Context

См. `proposal.md` и `specs/`: пока есть только каталог `apps/` и документы; приложений,
миграций, общего Compose и готового Битрикса нет. ТЗ требует реальный Битрикс как
единственный источник продуктового контента. Кирилл разрешил временную локальную
подмену для первого сценария; это не изменение требований клиента. Двойники лежат
в отдельном игнорируемом репозитории и в этот сценарий не включаются.

## Goals / Non-Goals

**Goals:**
- Проверить путь локальный источник -> получение контента Symfony -> публичный API -> Next.js.
- Сохранить заменяемую границу источника и возможность повторного запуска без дублей.
- Сделать режим подмены явно локальным и различать готовность первого сценария и OPS-005.

**Non-Goals:**
- Эмулировать админку и нативный API Битрикса или выбирать его редакцию/лицензию.
- Реализовывать учёт мест, регистрацию, платёжный шлюз, почту, роли, мобильную
  авторизацию, Unleash, RU/EN и поиск/фильтры в первом сценарии.
- Обещать окончательный контракт Битрикса или полноценный запуск на чистой машине
  с Битриксом и двойниками.

## Decisions

### 1. Подмена только на входе получения контента

Локальный мок-сервис отдаёт несколько вымышленных опубликованных и неопубликованных
мероприятий по HTTP в собственном небольшом формате с устойчивыми внешними ID.
Symfony получает их через отдельный компонент чтения источника и нормализует в
свою проекцию. Следующий change добавит адаптер настоящего Битрикса, не меняя
публичный API и путь импорта. Не объявляем формат мока нативным форматом Битрикса.
Режим источника выбирается явно; конфигурация обычного режима с моком отклоняется.

Альтернативы: прямой seed в PostgreSQL быстрее, но нарушает границу происхождения
данных и не проверяет путь импорта; поднимать сейчас настоящий Битрикс сохраняло бы
целевой путь, но блокировало бы первый сценарий на Q-010. Временная подмена —
исключение только для разработки; до приёмки контент должен поступать из Битрикса.

### 2. Проекция и повторная загрузка

В Symfony хранятся только нужные для чтения поля мероприятия, программы, спикеров и
площадки, с уникальным внешним ID и признаком публикации. Импорт по этому ID
обновляет существующую запись, а не создаёт новую при перезапуске. Сначала
проверяется целостность полученной партии, затем она применяется транзакционно:
ошибочная партия не оставляет полуприменённые данные; последняя корректная версия
остаётся для чтения. На старте окружение готовит схему и запускает начальный импорт
с ограниченным ожиданием доступности источника. Проверка готовности первого
сценария требует доступных страниц и хотя бы одного импортированного мероприятия.

Альтернатива — проксировать мок из Symfony без хранения: проще на старте, но не
проверяет границу синхронизации и усложняет будущую замену на Битрикс. Здесь нет
транзакций по местам или пользовательским данным; их проектируют отдельно.

### 3. Публичные поверхности минимальны

Symfony предоставляет публичные чтения `/api/v1/events` и `/api/v1/events/{id}`.
Второй маршрут ищет устойчивый внешний ID; неопубликованный и неизвестный ID
дают одинаковое отсутствие публичного результата. Next.js получает только эти
ответы, отображает `/` как каталог и `/events/{id}` как страницу, различает
загрузку, пустой результат, недоступность API и отсутствие мероприятия. Дату
показывает с часовым поясом мероприятия. Число свободных мест и кнопку записи
не показываем: проекция вместимости не является учётом занятых мест.

Альтернатива — читать мок прямо из Next.js: это дублировало бы контентный API и
скрыло бы несоблюдение архитектурной границы. Параметры фильтрации, английская
локаль и обещания о поисковом превью вводятся следующими changes.

### 4. Локальный запуск

Compose объединяет PostgreSQL, API, сайт и мок. Одна документированная команда
создаёт локальные настройки из шаблонов, подготавливает зависимости и схему,
запускает сервисы и проверяет весь первый сценарий. Контейнеры используют
требуемые версии PHP/Symfony и Next.js/TypeScript/Tailwind; выбор совместимых
образов и точных версий проверяется при реализации. Данные PostgreSQL находятся
в именованном томе, обычная остановка и повторный запуск его не удаляют.
Команда проверки сообщает отдельные ошибки подготовки, API, импорта и сайта.

Альтернатива — расширить Compose двойников или сейчас добавить Битрикс:
источник двойников при чистом клонировании неизвестен (Q-011), а установка
Битрикса не проверена (Q-010). Их добавление — отдельный этап до полного OPS-005.

## Risks / Trade-offs

- [Мок маскирует расхождение с реальным Битриксом] -> не считать CMS-001/CMS-004
  выполненными; отдельный change для контракта, реального импорта и чистого запуска.
- [Локальный режим случайно попадает на стенд] -> явное разрешение мока только
  в локальной конфигурации и проверка запрета при запуске обычного режима.
- [Недоступность источника или невалидная партия] -> ограниченное ожидание при
  подготовке, видимая ошибка импорта, отсутствие частичного обновления.
- [Пустой каталог принимают за готовую загрузку] -> проверка первого сценария
  требует демонстрационное мероприятие и открытие его страницы.
- [Название change шире этого шага] -> задачи и свидетельства ограничены первым
  сценарием; OPS-005 и исходное требование к Битриксу остаются открытыми.

## Migration Plan

Новые компоненты не требуют миграции существующего продукта. Для локального
обновления применяются совместимые миграции проекции; откат к предыдущему коду
не должен автоматически удалять том или данные. Перед включением реального
Битрикса отдельное изменение определит сопоставление внешних ID и способ
переноса или очистки только демонстрационной проекции без потери пользовательской
истории; в этом change пользовательская история ещё не создаётся.
