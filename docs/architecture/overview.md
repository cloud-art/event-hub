# Архитектура — WIP

## Обязательные границы
```text
Битрикс ── контент ──> Symfony API <── запросы ── Next.js
                           │
                           ├── PostgreSQL
                           ├── платёжный шлюз (двойник)
                           ├── SMTP (двойник)
                           └── API партнёра (дополнительное задание)
```

Битрикс: контент, вместимость, публикация. Symfony: места, участники,
записи, расчёты, доступы. Next.js: интерфейс. Прямого доступа сайта к Битриксу нет.

## Рабочая основа стека
Обязательное по ТЗ: PHP 8.5, Symfony 8.1, PostgreSQL, Next.js 16,
TypeScript, Tailwind, Битрикс. Приложения пока не установлены.

Предложенная основа, подлежащая проверке при реализации:
- Модульный монолит Symfony, Doctrine ORM/DBAL и миграции.
- PostgreSQL как источник истины о местах, транзакционная защита бронирования.
- REST JSON и OpenAPI; типизированный frontend-клиент из контракта.
- Messenger с PostgreSQL transport, transactional outbox для надёжных фоновых действий.
- Redis для кеша и ограничения запросов, не для окончательного учёта мест.
- Локальная проекция контента: уведомление Битрикса, получение актуальной версии, периодическая сверка.
- Next.js SSR для публичных страниц; next-intl, shadcn/ui, дизайн-токены.
- Docker Compose для воспроизводимого окружения.

## Уточнения после интервью
Источник: [planning-interview](../product/planning-interview.md); статус всех
пунктов — подтверждено для планирования, не согласовано заказчиком.
- Мобильная авторизация входит в текущий объём: access/refresh с ротацией и отзывом,
  браузер — HttpOnly cookie и защита от CSRF. Формат/сроки токенов ещё не выбраны.
- Unleash управляет флагами; Symfony вычисляет их для сайта и мобильного клиента,
  отдаёт клиентам только необходимые результаты и сам проверяет доступность API-операций.
- Нет прямых SDK Unleash в Next.js/мобильном клиенте на старте; серверный SDK
  использует полученную конфигурацию без сетевого обращения на каждый запрос.
- Назначения организаторов из Symfony отражаются в правах Битрикса;
  схема интеграции, отзыв доступа и создание мероприятий ещё требуют проработки.
- Экспорт выполняется фоном; права проверяются и при скачивании файла.
- Публикацию/проверку выполняем в среде, которую позже предоставит проверяющий.
- Предпочтительный способ доставки двойников — закреплённый Git submodule,
  только после проверки доступности источника. Пока product-test остаётся игнорируемым.

Форматы контрактов, машины состояний, аутентификация, библиотеки и версии
дополнительных зависимостей ещё не закреплены реализацией. Существенные
решения с альтернативами фиксировать в ADR по мере их принятия.

## Существующие двойники
Рабочие меры защиты от нагрузки и ответы интервью: [load-planning](load-planning.md).

Определены в `product-test/docker-compose.yml`; создают сеть `eventhub-doubles`.
Наше окружение может подключаться к ней как к внешней после запуска двойников.

| Сервис | Внутри сети | С хоста по умолчанию |
| --- | --- | --- |
| Шлюз | http://gateway:8080 | http://localhost:8081 |
| Партнёр | http://partner:8080 | http://localhost:8082 |
| SMTP через Toxiproxy | smtp:1025 | localhost:1025 |
| Mailpit UI | http://mailpit:8025 | http://localhost:8025 |
| Toxiproxy API | http://toxiproxy:8474 | http://localhost:8474 |

Для шлюза разделять внутренний API URL, публичный URL страницы оплаты и
доступный шлюзу callback URL. Текущий callback в примере окружения указывает
на `host.docker.internal:8000`; адрес API в контейнерах ещё не определён.

PostgreSQL, Redis, Битрикс и приложения не входят в Compose двойников.
Версии PHP и MySQL/MariaDB для Битрикса выбираются отдельно по совместимости.
