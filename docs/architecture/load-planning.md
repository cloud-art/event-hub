# Нагрузка — рабочие гипотезы

Статус: результаты планирования, не согласованные с заказчиком требования
и не свидетельство реализации. Связанные требования: NFR-001, NFR-002, EVT-002,
PAY-002, PAY-003, REG-003. Решения уточняются по результатам нагрузочных проверок.
Полная запись ответов: [planning-interview](../product/planning-interview.md),
INT-043–INT-053; ссылки Q ниже обозначают только номера вопросов интервью.

## Превентивные меры
- Кешировать публичный контент отдельно от динамического остатка мест и персональных данных.
- Перед открытием регистрации прогревать популярные страницы; защищать пересборку кеша от одновременного выполнения множеством запросов.
- Сократить транзакцию бронирования до проверки условий и выделения мест. Вызовы шлюза и почты выполнять вне блокировок мест.
- Ограничить соединения с БД, параллелизм воркеров и ожидание блокировок; не допускать неограниченного накопления запросов.
- Изолировать письма и экспорт от обработки платежей и освобождения броней отдельными очередями и процессами.
- Ограничить опрос остатка интерфейсом, разнести запросы по времени, приостанавливать опрос в неактивной вкладке.
- Применять идемпотентность записи и платежей, ограниченные повторы с задержкой и случайным разбросом.
- При перегрузке приоритизировать уведомления оплаты, отмены и истечение броней относительно новых попыток записи.

## Ответы интервью
- Q43: отдельно проверять 5 000 посетителей за 3 минуты и конкуренцию за последние места, включая группы; сверять итоговое состояние БД.
- Q44: предварительные цели p95 — 500 мс для API чтения и 1 с для оформления брони; менее 1% непредвиденных серверных ошибок на согласованном профиле и оборудовании. Ожидаемые отказы учитывать отдельно.
- Q49: при достижении безопасного предела допустим контролируемый отказ новой записи с понятной повторной попыткой, сохранением введённых данных и защитой от дублей.
- Q50: начать с отдельного лёгкого endpoint остатка и ограниченного опроса активной страницы. Интервал выбирать по допустимой задержке и измерениям; 15 секунд не закреплены. SSE рассмотреть по результатам раннего нагрузочного теста, если опрос создаёт существенную нагрузку или не обеспечивает требуемую актуальность. WebSocket для одностороннего обновления остатка пока не нужен.
- Q51: отдельные очереди и процессы Messenger для изоляции медленных задач; без выделения микросервисов.
- Q52: при сбое обновления контента допустима последняя корректная версия; без авторитетного учёта мест новые записи запрещены, устаревший остаток не выдаётся за актуальный.
- Q53: виртуальная очередь — резервный вариант по результатам раннего нагрузочного прототипа, до завершения всего интерфейса.

Q43–Q53 здесь — номера вопросов интервью, не ID требований и не ID реестра
`docs/product/open-questions.md`.

## Ограничения
Масштабирование API не устраняет конкуренцию за инвентарь одного мероприятия.
Push-обновление интерфейса не заменяет транзакционную проверку места.
Поведение при перегрузке и допустимая задержка отображения требуют согласования.
