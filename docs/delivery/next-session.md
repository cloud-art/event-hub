## Следующий порядок работы
1. Прочитать `AGENTS.md`, интервью, реестр вопросов и пакеты согласования.
2. Разобрать Q-015–Q-023: внутренние пробелы/развилки. Не выдавать рекомендации за решения.
3. Проверить внешние зависимости: лицензия/автоустановка Битрикса,
   доступность источника двойников и применимость submodule. Локально product-test
   существует как отдельный репозиторий, но исключён из корневого Git и не доставляется при клонировании.
4. Составить первоначальную оценку при 30 часах в неделю с резервом на приёмку;
   отделить обязательное ТЗ от расширений интервью. Даты и оборудование пока не подтверждены.
5. Подготовить приоритетные письма/пакеты заказчику; не считать их отправленными
   или согласованными без подтверждения. Финансовые правила и доступы — блокеры затронутых реализаций.
6. Актуализировать proposal, затем создать specs/design/tasks по инструкциям CLI
   и выполнить `openspec validate bootstrap-local-environment --strict`.
7. После отдельного разрешения на apply реализовать первый технический вертикальный
   сценарий: воспроизводимый запуск → настоящий Битрикс → Symfony → Next.js.
   Новые компоненты вводить под конкретные задачи; участие/оплата в этот шаг не входят.

## Не забыть при оценке
Предложения сверх явно расписанного в ТЗ: мобильная авторизация уже сейчас,
автосинхронизация прав Битрикса, Unleash, фоновые экспорты с защищённым скачиванием,
административный повтор задач, копии/проверка восстановления и уведомления сопровождению.
Всё это подтверждено для планирования, но не согласовано заказчиком и не оценено.
Партнёрские воркшопы — только дополнительное задание, подробно ещё не проектировались.

## Проверки и ограничения на момент подготовки
- Приложения, общий Compose/Makefile, CI, тесты и матрица свидетельств ещё не реализованы.
- Контейнеры двойников и приложения в этой сессии не запускались.
- Проверки документов и Git выполняются перед фиксацией; результат коммита/push
  сообщается в итоговом ответе, а не предсказывается этим файлом.
- Не считать отсутствие ошибок Markdown или готовность proposal доказательством готовности продукта.

## Быстрый вход


артефактов; прежде получить актуальный контекст и разрешить материальные неоднозначности.
