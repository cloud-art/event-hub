# Согласование рабочих гипотез

## Разделение источников
1. [requirements](requirements.md) — требования предоставленного ТЗ.
2. [planning-interview](planning-interview.md) — подтверждённые Кириллом предложения для планирования.
3. Письменные ответы заказчика — отдельное основание изменения требований.

Для каждого исходного ID статус **согласовано клиентом (исходное ТЗ)** означает
только постановку из ТЗ; он не распространяется на её толкование, критерии
приёмки и способ реализации. Гипотеза INT не согласована, пока соответствующее
правило не подтверждено письменно в [журнале](approval-packages.md).
Ответ по одному правилу не подтверждает остальные части INT. Техническая проверка не
означает продуктового согласования.

## Запись решения
Использовать ID INT из интервью или Q из открытых вопросов, не заводить дубли
того же решения. В репозитории достаточно связанных ID, краткой сути вопроса,
факта отправки и статуса. После ответа добавить дату и источник/ссылку на письмо,
точное решение и условия; полные тексты писем и их черновики здесь не хранить.

Статус согласования: `не согласовано клиентом` (гипотеза или отправлено на
согласование) → `согласовано клиентом` / `отклонено клиентом` после письменного
ответа. Отдельно отмечать факт отправки, не смешивая его с согласием.
При новом предложении после отказа сохранить прежнее решение и основание пересмотра.
Отметку «на согласовании» ставить только после фактической отправки; молчание не означает согласие.
В [approval-packages](approval-packages.md) зафиксированы факт первого письма
и темы следующих обращений; тексты писем готовятся отдельно.

## Граница реализации
- Обратимые технические части допустимы на явно обозначенных гипотезах.
- Правила денег, доступа и отмены сначала письменно согласовать для затронутого сценария.
- Установка Битрикса, условия использования пробной версии и доставка двойников —
  наши технические задачи; неподтверждённые условия не объявлять обеспеченными.
- OpenSpec change должен указывать связанные INT/Q, их статус и блокеры.
- Готовность плановых артефактов, согласование и проверенная реализация — три разные оси.
  Успешный `openspec validate` не заменяет ни согласование, ни тесты.

## После ответа заказчика
Сопоставить ответ с исходным ТЗ и гипотезами, обновить реестр и затронутые
OpenSpec-артефакты. При влиянии на объём обновить оценку и перечень исключений.
Не закрывать связанные вопросы автоматически, если ответ разрешает только часть.
