# Согласование рабочих гипотез

## Разделение источников
1. [requirements](requirements.md) — требования предоставленного ТЗ.
2. [planning-interview](planning-interview.md) — подтверждённые Кириллом предложения для планирования.
3. Письменные ответы заказчика — отдельное основание изменения требований.

На момент фиксации интервью ответов заказчика нет. Не считать реплики Кирилла
согласованием заказчиком, а техническую проверку — продуктовым разрешением.

## Запись решения
Использовать ID INT из интервью или Q из открытых вопросов, не заводить дубли
того же решения. Для отправляемого предложения фиксировать:
- связанные требования, вопрос и предлагаемый ответ;
- обоснование, последствия и блокируемые сценарии;
- подтверждение Кирилла для планирования;
- статус согласования заказчиком;
- после ответа — дату, источник/ссылку на письмо, точное решение и условия.

Статусы: `гипотеза → на согласовании → согласовано / отклонено`.
При новом предложении после отказа сохранить прежнее решение и основание пересмотра.
Статус «на согласовании» ставить только после фактической отправки; молчание не означает согласие.
Материалы в [approval-packages](approval-packages.md) пока только черновики, не отправлены.

## Граница реализации
- Обратимые технические части допустимы на явно обозначенных гипотезах.
- Правила денег, доступа и отмены сначала письменно согласовать для затронутого сценария.
- Лицензия, доступ к зависимостям и среда проверяются как внешние зависимости;
  неподтверждённые условия не объявлять обеспеченными.
- OpenSpec change должен указывать связанные INT/Q, их статус и блокеры.
- Готовность плановых артефактов, согласование и проверенная реализация — три разные оси.
  Успешный `openspec validate` не заменяет ни согласование, ни тесты.

## После ответа заказчика
Сопоставить ответ с исходным ТЗ и гипотезами, обновить реестр и затронутые
OpenSpec-артефакты. При влиянии на объём обновить оценку и перечень исключений.
Не закрывать связанные вопросы автоматически, если ответ разрешает только часть.
